## Fixed findings

The three HelmReleases previously used remediation retries. A failed install can
then trigger uninstallation, and a failed upgrade can trigger rollback. For storage,
that can delete generated credentials or reverse software after state migration.
They now use `RetryOnFailure` for both installation and upgrade. This leaves failed
resources available for investigation and retries in place. Operators must still
respond to failed reconciliations; automatic retries are not a recovery plan.

Validation now asserts that strategy for every storage release. Existing checks
still verify class ownership/replicas, CNPG mutation scope, dependency ordering,
Garage's rendered TOML and single-node initialization, and absence of an unsolicited
backup target. All **118 rendered resources passed strict schema validation**, with
zero invalid, errors or skipped schemas. Charts were rendered using Helm 4.3.0.
The disposable kind admission-policy test remains on Kubernetes 1.36.4 to exercise
the previous bootstrap patch; fresh bootstrap defaults advance to 1.36.5.
Its initial GitHub Actions run exposed a CRD discovery/admission-cache startup race:
the API temporarily returned `ServiceUnavailable` after the CRD was Established.
The readiness probe now retries that specific response within its existing bounded
wait, surfaces API diagnostics, and still fails immediately on other admission errors.

CI actions are updated and commit-pinned; Helm/Kustomize/kubeconform validation
tools are current and checksum-verified. The generated manifests are validated
against the new Flux 2.9.6 schemas.

No cluster, disk, PV, credential or existing backup was inspected. The audit cannot
confirm that a real cluster is healthy enough for this upgrade. No volumes were
created/deleted, no replication factor was silently changed, and no backup endpoint
or credential was invented.

## Upgrade procedure

1. Confirm actual installed versions and read the upstream release notes. Longhorn
   1.13.0 requires Kubernetes >=1.34; this stack requires >=1.36 for its admission
   policy. Longhorn supports the adjacent 1.12.x → 1.13.x transition. Older minor
   releases need intermediate upgrades; do not simply point them at this branch.
2. Ensure every volume/replica is healthy, capacity is available, no failed backing
   image blocks the upgrade, and required host iSCSI/mount checks pass. Export a
   Longhorn system backup and create independent application/data backups. Test
   restoration. Do not upgrade faulted volumes without a recovery plan.
3. Reconcile the companion Flux/Gateway update first. During a maintenance window,
   reconcile storage and require each child and HelmRelease to be Ready at the new
   revision. Verify the CNPG webhook/operator and actual native defaulting behavior.
4. After the Longhorn manager update, complete the V1 engine upgrades using the
   supported Longhorn workflow. A Helm chart upgrade alone does not prove every
   existing volume engine is updated. V2 is still disabled in this repository.
5. Verify existing PVC mounts, a disposable PVC read/write/reattach, database
   transactions and an S3 write/read. Observe degraded-volume and controller events.
6. Diagnose failures in place. **Do not downgrade Longhorn after a successful
   upgrade.** Git revert is not a supported database/storage rollback. Suspend a
   failing reconciliation only deliberately, preserve diagnostics, and use upstream
   recovery or a tested restore when state has changed.

The operator patch does not upgrade PostgreSQL major versions. SSO remains on 17.11;
18.6 needs its own tested migration and recovery plan.
